Architecture Approaches — Custom Token Feature

How should the wizard, AI generation, and checkout integration be structured?

A

Route-Per-Step Wizard (Recommended)

Each wizard step is its own nested route under /custom-token. State persists in the URL + session. Back/forward navigation works natively.

Routes:
/custom-token → landing (pick path)
/custom-token/we-design/occasion
/custom-token/we-design/description
/custom-token/we-design/material
/custom-token/we-design/engraving
/custom-token/we-design/review
/custom-token/you-design/describe
/custom-token/you-design/preview
/custom-token/you-design/refine
/custom-token/you-design/material
/custom-token/you-design/review

Pros

  • Native browser back/forward
  • Each step has its own loader/action — clean separation
  • URL-shareable progress (bookmark mid-wizard)
  • Follows existing Hydrogen routing patterns
  • SEO-friendly (each step is indexable or not)

Cons

  • More route files to manage
  • State handoff between routes needs session or search params
  • Full page transitions between steps (mitigated by animations)
B

Single-Page Wizard (Client-Side State)

One route (/custom-token) renders all steps. A React state machine manages step transitions. AI calls go through a single action endpoint.

Structure:
/custom-token → single route, all steps client-side
/api/custom-token/generate → action for AI generation
/api/custom-token/upload → action for image uploads
State machine: idle → occasion → description → material → engraving → review

Pros

  • Smooth step transitions (no page reload)
  • All state in one component tree — easy to pass between steps
  • Fewer files
  • Can animate between steps with Framer Motion

Cons

  • Browser back button breaks flow (needs manual handling)
  • Loses progress on page refresh unless saved to session
  • Large single component — harder to maintain
  • Doesn't follow existing route-per-page pattern
C

Hybrid: Layout Route + Client Steps

A parent layout route (/custom-token) manages shared state and progress UI. Two child routes for each path. Steps within each path are client-side with URL hash tracking.

Structure:
/custom-token → layout (progress bar, shared state)
/custom-token/we-design#step=occasion → client steps
/custom-token/you-design#step=describe → client steps
Actions handled via useFetcher from shared layout

Pros

  • Smooth transitions within a path
  • Shared layout for progress bar and nav
  • Two main routes — not too many, not too few
  • State scoped to each path's component

Cons

  • Hash-based steps are a workaround, not native routing
  • Still needs manual back-button handling within steps
  • Mixed pattern — some things are routes, some aren't
  • Harder to reason about than pure route or pure client approach

💡 Recommendation: Option A

Route-per-step is the most Hydrogen-native approach. It leverages your existing loader/action patterns, gives you clean separation of concerns (each step validates independently), and browser navigation just works. The "more files" trade-off is worth it — each file is small and focused. Session storage handles state between steps cleanly.
